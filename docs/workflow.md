# 工作流

1. 记录来源文件、版本标识、授权的匿名化与发布边界，并记录实际工具版本与关键运行条件。
2. 本地 PDF 可访问且 MarkItDown 可用时，先实际运行 MarkItDown 生成 Markdown；转换结果是候选层，原 PDF 仍是复杂表格、矩阵、双栏、公式和异常页面的复核依据。工具不可用或转换异常时，记录实际 fallback 及原因。
3. 用 `scaffold` 建立候选目录；提取表格和矩阵时保留页码、符号和 `extracted`/`needs_review` 状态。
4. 对有歧义的单元格逐项视觉复核；不要用相邻单元格、模糊字形或旧 JSON 代替证据。
5. 运行 `scripts/curriculum.py validate <program.json>`。修复结构错误或保留未知项；警告是诊断，不是质量、达成或发布结论。
6. 用 `diff` 比较新旧版本。保留旧 JSON，新版本独立存放，并把冲突列为待处理或有来源支持的变更。
7. 用 `generate_skill.py` 生成独立专业 Skill，并在生成目录运行一次 `validate`。
8. 仅在获准范围内匿名化。需要把 Markdown 交付为 DOCX、HTML、PDF 或其他 Pandoc 支持格式时，优先用 Pandoc 转换并检查目标文件；导出成功与版式检查不替代内容核验。
9. 完成本次复盘：记录问题与证据，判断经验适用范围，检查与旧规则的冲突，并为下次运行写出可执行的预防条件。只有获得支持的经验才更新通用工作流或风险表。

每个阶段都保留“官方直接”“派生”和“未解决”三个边界。课程大纲中没有来源的字段保留 `待编制`。
